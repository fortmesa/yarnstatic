# @fortmesa/yarnstatic

Node.js CLI port of [yarnstatic](../README.md) (`check`/`fetch`/`serve`/
`version`) -- an alternative to the Go binary for environments that have
Node but not Go (e.g. restricted CI base images). This is not a
replacement: the Go binary stays canonical for
`plugins/yarn-plugin-yarnstatic` (the daemon-based Yarn plugin). This
package also bundles `yarn-plugin-yarnstatic-s3` (the direct-S3 Yarn
plugin, no daemon required) for a self-contained, Node-only setup.

See [`../docs/architecture.md`](../docs/architecture.md) for why this
tool exists at all, and [`../docs/cli.md`](../docs/cli.md) /
[`../docs/protocol.md`](../docs/protocol.md) for the full CLI/exit-code
and wire-protocol reference this package implements.

## Install

```sh
yarn add -D @fortmesa/yarnstatic
```

This places a `yarnstatic` binary at `node_modules/.bin/yarnstatic`. Then
wire up the bundled direct-S3 Yarn plugin (one-time, per project):

```sh
yarn plugin import ./node_modules/@fortmesa/yarnstatic/plugin/plugin-yarnstatic-s3.cjs
export YARNSTATIC_BUCKET=my-verdaccio-bucket
yarn install --immutable
```

Or use the CLI directly, without the plugin, e.g. in CI to verify a
lockfile is fully mirrored in S3 before relying on an offline install:

```sh
yarnstatic check --bucket my-verdaccio-bucket .
```

**Do not install this package alongside the daemon-based
`yarn-plugin-yarnstatic` in the same project without understanding the
interaction**: that plugin's `resolveBinary()` searches
`node_modules/.bin/yarnstatic` (among other locations) and spawns whatever
it finds there with `serve --socket <path>` (see
[`../docs/plugin.md`](../docs/plugin.md#binary-resolution)). Since this
package's `yarnstatic` binary implements `serve` against the same
documented wire protocol, it works correctly as that plugin's daemon too --
this is a deliberate design goal, not an accident, and has been verified
end-to-end against the unmodified plugin. But if you only want the bundled
`yarn-plugin-yarnstatic-s3` path, be aware the daemon plugin will pick this
binary up automatically if both are present in the same project.

## Commands

- `yarnstatic check [flags] [path]` -- verify every `npm:`-protocol,
  checksummed `yarn.lock` entry exists in the configured S3 bucket.
- `yarnstatic fetch [flags] --package <name>@<version> [--out file]` --
  one-shot manual/debug download.
- `yarnstatic serve --socket <path> [flags]` -- the daemon
  `yarn-plugin-yarnstatic` talks to. Not meant to be invoked directly.
- `yarnstatic version` -- prints this package's own `package.json` version
  (the Go binary bakes its version from a release git tag via `-ldflags`
  at build time; there's no direct Node equivalent, so this is the one
  command whose underlying *mechanism* intentionally differs, not just its
  wording).

Flags, environment variables, and exit codes are identical to the Go
binary's -- see [`../docs/cli.md`](../docs/cli.md) -- with one accepted,
documented divergence: a `--profile` that doesn't exist fails at S3
*client construction* in Go (exit code 3), but `@aws-sdk/client-s3`
resolves credentials lazily, so the equivalent failure in this CLI only
surfaces on the first request, as `KindNoCredentials` (exit code 4, not
3). See `src/s3client/client.js`'s `classify()` for where this is handled.

## Development

```sh
yarn install
yarn test          # test/smoke.js, no framework, node:assert/strict
yarn pack           # runs the prepack script, builds the bundled plugin fresh
```

`plugin/plugin-yarnstatic-s3.cjs` is generated by `scripts/build-plugin-bundle.js`
(wired as `prepack`) from `../plugins/yarn-plugin-yarnstatic-s3`'s own
`yarn build` output -- it's gitignored and should never be hand-edited or
committed.

### Publishing

This package publishes only through `../.github/workflows/release.yml`'s
`publish-npm` job, triggered by the same `v*.*.*` tag push as every other
release artifact in this repo -- there is no manual publish path, and
`yarn npm publish` should never be run by hand from a workstation. That job
authenticates to `npmjs.dev.fort.blue` via a GitHub Actions OIDC token
(same pattern as `verdaccio-security-filter`'s own release pipeline), and
skips cleanly if `package.json`'s version is already published (this
package's version is independent of the repo's own git tags, same as
`yarn-plugin-yarnstatic-s3`'s own `package.json` version already is -- bump
it manually before tagging a release that should also publish a new
version of this package).

### `classify()` verification status

`src/s3client/client.js`'s `classify()` local-failure branches were
verified against the actually-installed SDK (`@aws-sdk/client-s3@3.1079.0`)
using only local-validation scenarios -- fake static credentials plus a
bad `--region`/`--endpoint` value, so nothing ever reaches a real AWS
endpoint. Confirmed real shapes:
- no credentials resolvable at all -> `CredentialsProviderError`
- a `--profile` that doesn't exist -> `CredentialsProviderError`
- a malformed `--endpoint` URL -> `EndpointError`
- an invalid `--region` string -> a **plain `Error`**, no typed class at
  all (`"Region not accepted: region=\"...\" is not a valid hostname
  component."`) -- this is why `classify()`'s message-substring fallback
  still matters even though the other three cases are typed.

The API-error-code branch (`S3ServiceException`, `notFoundCodes`/
`accessDeniedCodes`) is exercised with real instances of the SDK's own
exported `S3ServiceException` class in `test/smoke.js`, not live S3
responses. If `@aws-sdk/client-s3` is upgraded and something in
`classify()` seems to misclassify, re-run the same kind of local-only
probe (invalid region/endpoint/credentials, never a real bucket) before
assuming the fix -- don't hand-invent new substrings.
